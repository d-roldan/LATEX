Esta es una **lectura en vivo de la API de DBS**. DBS puede conservar un registro interno entre adquisiciones, y no se demostró la edad exacta del último dato Modbus ni la escala física de temperatura. La respuesta completa sólo se acepta cuando DBS reconoce la IP y entrega la firma y longitud esperadas; una respuesta incompleta, de otra IP o sin `*` se descarta. `cms_timestamp` del nuevo flujo es el instante de recepción de la respuesta en Node-RED, no una marca temporal emitida por la inyectora. `adquisicion_industrial_fresca` permanece `NO_VERIFICADA`.

El flujo inicia una consulta `0` por cada una de las cinco máquinas en paralelo, con un nodo TCP dedicado por IP. Para cada máquina espera la respuesta antes de solicitar `8` y luego `2`; así nunca hay dos consultas simultáneas de una misma IP en un nodo TCP. Repite la ronda cada ocho segundos y publica sólo al completar las tres respuestas de la misma ronda. El estado de caché se pierde al reiniciar el backend, por lo que el flujo deberá enviar una nueva ronda.

### Opción MQTT mostrada en DBS

Las capturas del 19/10/2026 muestran en Preferencias de DBS la casilla **«Uso de transmisión de datos Mqtt basada en shot»** desmarcada, host del broker vacío y puerto `1883`. El `SystemConfig.ini` de producción confirma `use_mqtt_transfer=0`. La otra pantalla muestra `127.0.0.1:5000` y velocidad API de `1000 ms`; esos valores no configuran un broker MQTT.

El binario DBS de la misma versión contiene rutas de publicación `Woojin/%1/ShotBasedSetData` y `Woojin/%1/ShotBasedActData` (REA `ev_f6fefaa9095fe6e8bd18471e24c16f16fd8c248f329ba91aceb1c4416721142b` y `ev_5065be237457b2dbc4468b94167480953f046815883046c7f100b770eeeaef10`). VA `0x4A7C40` construye `QMQTT::Message` y llama a `QMQTT::Client::publish` si hay conexión (REA `ev_f3fdb072832f04c38add1628d9e8a5cbf4e9e81d1f593b74b012c118212403c3`). Esta evidencia confirma una ruta de publicación **asociada a disparos** y dos clases de mensaje, pero no demuestra el contrato completo de payload, la identidad exacta de `%1`, la frecuencia real, ni que publique estados y temperaturas actuales entre disparos. Tampoco se observó un broker configurado o una publicación real.

Para el objetivo de tarjetas ENVASES con estado, producción y temperaturas continuamente actualizables, mantener la API TCP de lectura como fuente principal una vez retirado el bloqueo de IP. Evaluar MQTT como fuente complementaria para historial por disparo sólo después de identificar un broker apropiado, capturar mensajes reales en una prueba acotada, verificar identidad de máquina y marcas temporales, y contrastar su esquema con la API. No activar la casilla MQTT en producción sólo por su presencia en la interfaz: por ahora no reemplaza la lectura `0/8/2` ni resuelve el bloqueo actual de `10.1.2.44` en DBS.

El backend conserva los campos de DBS en la lectura actual de ENVASES y, cuando está configurado `INFLUXDB_ENVASES_BUCKET`, escribe `woojin_status` y `woojin_dbs_temperature` con etiquetas de equipo y fuente. La gráfica histórica de temperatura ya existente sigue mostrando el último **disparo atribuido** (`woojin_shot`), no la serie continua de DBS. La serie `woojin_dbs_temperature` queda almacenada para consultas futuras; no se ha añadido una gráfica de esa serie. Las filas de `disal_cms.real_data` y `shot_data` detenidas el 17/10/2026 no se importan ni se presentan como actuales.

### Lectura completa desde Node-RED; publicación rechazada

A las 09:17 del 19/10/2026, Debug del Node-RED externo mostró para las cinco IP `DBS_RESPUESTA_VALIDADA` de tipo `0` (86 campos) y `8` (5 campos), seguido de `DBS_LOTE_PREPARADO`. Ese último evento sólo se emite después de aceptar también la respuesta `2` de la misma ronda. Se confirmó, por tanto, la consulta `0 → 8 → 2` y el armado de un lote para cada máquina desde `10.1.2.44`. Inmediatamente después, los cinco POST recibieron `ERROR_API` con HTTP `400`. No hay confirmación de aceptación, persistencia, InfluxDB ni actualización del panel.

La versión original del flujo omitía el cuerpo de error de ApiDisal; el código HTTP `400` por sí solo no identifica qué regla falló. El backend de este repositorio exige validación estricta (`forbidNonWhitelisted`) y su DTO nuevo admite `telemetry_origin`, `target_quantity`, `defective_quantity` y `dbs_temperature_zones`; una versión productiva anterior podría rechazar esas propiedades. Esto es una hipótesis hasta leer `message` de la respuesta HTTP o comprobar la versión productiva. También podría fallar una validación de rango de un valor real.

El JSON importable actualizado agrega el nodo Debug **«Lectura decodificada · activar para ver datos»**, inicialmente apagado. Al habilitarlo muestra el lote justo antes del POST: IP, modelo, estados, cantidades, tiempos y ocho pares de temperaturas en `msg.payload.maquinas[0]`. Es una vista de datos industriales, sin la clave de integración. El nodo **«Verificar aceptación y persistencia»** ahora incluye en `ERROR_API` `motivo`, hasta ocho mensajes de `validacion` y `total_errores`, acotados en longitud; no muestra el cuerpo íntegro de la respuesta ni los encabezados. Para usarlo, deshabilitar la pestaña anterior, importar este JSON actualizado, configurar las mismas variables de entorno, habilitar la nueva pestaña y desplegar sólo los nodos modificados. Activar el Debug de lectura sólo durante la comprobación. No dejar dos pestañas publicando a la vez.

Si `validacion` dice `property ... should not exist` para los campos nuevos, actualizar el backend y frontend de ApiDisal mediante `docs/ACTUALIZACION_SERVIDOR.md` antes de reintentar. Si menciona un rango o tipo, corregir la normalización del campo señalado con evidencia de la respuesta DBS. Si `validacion` está vacío, revisar el cuerpo HTTP en un Debug temporal conectado a la salida de **«POST ApiDisal ENVASES»**, sin compartir claves ni encabezados. No se modificó ni desplegó el Node-RED externo desde este repositorio.

**Causa confirmada a las 09:32 del 19/10/2026:** el Debug conectado a la salida HTTP mostró `400 Bad Request` con cuatro mensajes: `maquinas.0.property telemetry_origin should not exist`, `target_quantity should not exist`, `defective_quantity should not exist` y `dbs_temperature_zones should not exist`.
